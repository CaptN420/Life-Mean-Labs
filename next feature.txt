0.CAPABILITY CREATION PRINCIPLE
Life_mean may detect missing capabilities during an experiment and propose the creation of a Tool, Thinker, or Worker. Creation is performed through the existing Code Lab development pipeline. Generated capabilities remain candidates and non-executable until validation and explicit human incorporation. Their origin, creator, permissions, version, hash, tests, and originating experiment are preserved as provenance.
1. Preserve Stable Core.
2. Experimental layers use Stable Core.
3. Deterministic-first; LLM when needed.
4. Downloaded extension != incorporated extension.
5. LLMs may REQUEST capabilities but cannot authorize themselves.
6. Human approval is required for dynamic incorporation.
7. Scientific execution must remain traceable to RAW.
8. Research packages carry evidence.
9. Extension packages carry executable capabilities.
10. Never encode the research hypothesis as architecture.


1. Visualisation live des agents dans Code Lab. C’est probablement le prochain ajout le plus satisfaisant. Montrer en temps réel Planner → Developer → Critic → Tester → Reviewer, quel modèle travaille, ce qu’il est en train de faire, fichiers modifiés, tests lancés, erreurs, patches, validations et événements EventBus. Il faut afficher les vraies actions backend, jamais une animation simulée. Idéalement une timeline du genre Developer → écrit game.py → Pytest FAIL → Critic → diagnostic → Developer → patch → Pytest PASS.
2. Finir et geler le baseline. Avant les gros nouveaux systèmes : wheel réellement installable hors du repo, ressources/personas/dashboard correctement packagés, suppression des chemins machine, correction de la race de lifecycle, dependency injection Code Lab, suite pytest propre, Autopilot réellement accessible depuis son onglet, Settings réellement connecté à la configuration, et preuve UI → API → Stable Core → RAW. Une fois ça vert : tag du baseline et on arrête de déplacer ses fondations.
3. Migration du frontend vers TypeScript. C’est déjà une décision approuvée : remplacer progressivement le gros dashboard.html par une application modulaire, sans toucher au Stable Core Python. Architecture approximative : pages/Debate.tsx, Autopilot.tsx, CodeLab.tsx, Settings.tsx, puis Research.tsx et Extensions.tsx, avec un client API typé commun. Python reste le moteur; TypeScript devient l’interface interchangeable.
4. Autopilot scientifique avec trois modes. MULTI_AGENT, SINGLE_MODEL et COMPARISON. Comparison exécute les deux conditions successivement avec mêmes tâches/seeds/validators/protocole et conserve RAW-A et RAW-B. Comparer qualité, tests déterministes, tokens, temps, VRAM, échecs et éventuellement énergie/coût. Life_mean ne doit jamais conclure « 4×4B = 12B » universellement; seulement « performances comparables sous ce protocole et ce budget ».
5. Research Layer / mémoire personnelle du chercheur. Local-first et privé par défaut : Pseudonym → Question → Hypothesis → Experiment → Result → Claim → Notes. Le Lab capture automatiquement modèles, rôles, personas, hardware, paramètres, seeds, router decisions, versions et RAW. Le chercheur fournit surtout la question, l’intention, l’hypothèse et son interprétation. Conclusions et corrections restent versionnées; les anciennes ne disparaissent pas.
6. Carnet de bord + Research Ledger. Deux choses distinctes : le Carnet donne l’histoire lisible du parcours du chercheur; le Ledger contient les relations scientifiques précises. Il faut aussi les sous-ledgers thématiques, le Failure Bank, les hypothèses verrouillées avant résultat, les statuts OBSERVATION / SUPPORTED / CONTRADICTED / INCONCLUSIVE, et les liens exacts CLAIM → RESULT → EXPERIMENT → RUN → RAW.
7. .lmresearch. Package scientifique portable et documenté contenant protocole, configuration, personas/rôles, modèles, hardware pertinent, résultats, provenance, métriques et surtout Scientific RAW sanitizé. Les métriques devraient pouvoir être recalculées depuis le RAW. Import/export entre deux installations indépendantes sera le vrai test. Les packages sont immuables et reliés par REPLICATES, EXTENDS, CHALLENGES, CONTRADICTS, etc., plutôt que fusionnés.
8. Extension Lab : Workers / Thinkers / Tools. Une nouvelle page montrant clairement ce que possède le Lab : Workers, Thinkers et Tools, leurs versions, origine, état, permissions et compatibilité. Code Lab devient aussi Extension Builder : l’utilisateur décrit « crée-moi un Thinker statisticien », puis choisit développement SINGLE_MODEL ou MULTI_AGENT. Code Lab génère le package, les tests et le fait passer par la validation — sans l'activer automatiquement.
9. Packages .lmextension. Format séparé de .lmresearch pour le code exécutable : manifest, code, tests, permissions, version, hash, signature éventuellement. Une expérience référence les extensions exactes ID + version + hash, mais le code exécutable ne doit pas être silencieusement embarqué/activé par le package scientifique.
10. Extension Bank avec la règle essentielle DOWNLOADED ≠ INCORPORATED. Download et Download All placent les extensions dans une banque/quarantaine non exécutable. États possibles : DOWNLOADED → VERIFIED → TESTED → INCORPORATED → ENABLED, plus DISABLED, INCOMPATIBLE, QUARANTINED, FAILED_TESTS. Cliquer Incorporate enregistre l'extension auprès d'un ExtensionRegistry; ça ne copie jamais son code dans Stable Core.
11. La banque devient visible aux expériences. Autopilot/agents peuvent rechercher les métadonnées des extensions téléchargées. Un LLM peut constater « StatisticalVerifier existe dans la banque », mais il ne peut jamais se donner l'autorisation de l'exécuter. Il émet une INCORPORATION_REQUEST; TypeScript affiche une notification détaillée avec raison, modèle/agent demandeur, permissions, hash, tests et provenance. L'humain choisit Reject, Allow for this experiment ou Incorporate permanently. Un refus ne doit pas générer 50 nouvelles demandes.
12. Deterministic-first Capability Resolver. C’est devenu un principe central : chercher d’abord une capacité déterministe active; ensuite éventuellement une capacité déterministe présente dans la banque avec approbation; ensuite petit spécialiste LLM; puis raisonnement multi-agent/gros modèle si nécessaire. pytest, compilateur, parser, schema validator, calcul symbolique, etc. passent avant « demande au Judge s'il pense que c'est correct ». Deterministic result et semantic Judge restent séparés.
13. Extensions créées pendant une recherche = provenance scientifique. Si quelqu’un importe EXP-A, développe quatre nouveaux Workers et publie EXP-B, B doit déclarer exactement ces quatre nouvelles dépendances. Le prochain chercheur peut télécharger uniquement celles qui l'intéressent ou toutes celles nécessaires à une réplication exacte. Chaque extension garde auteur/créateur, version, hash, expérience d'origine et derived_from. Une ancienne expérience reste reproductible avec l'ancienne version.
14. Extension Catalog / futur écosystème. Recherche et extensions deviennent deux catalogues complémentaires. Pas de « ⭐ 4.9 = scientifiquement bon ». Montrer plutôt expériences qui l'utilisent, réplications indépendantes, résultats, failures connues, versions et provenance. Quelqu'un peut contribuer uniquement un Tool, un Thinker, un Worker ou une expérience sans modifier Life_mean Core.
15. Research Catalog / collaboration. Organisation plutôt Subject → Question → Hypothesis → Experiments/Results/Claims. Quelqu'un découvre une expérience et peut Inspect RAW, Replicate, Challenge, Extend, Respond. Les collaborations se forment autour des questions et des preuves plutôt qu'autour d'un réseau social générique.
16. Correspondance scientifique. Researcher Notes restent personnelles; Correspondence voyage avec les packages. Une communication n'est jamais automatiquement une preuve. Elle peut donner naissance à une hypothèse puis à une expérience. Les critiques visent méthode/résultat/interprétation, jamais la personne. Les contradictions et résultats négatifs restent visibles.
17. Git/repository comme distribution, DB comme index. Packages/Git restent la source portable/versionnée; SQLite/Postgres/embeddings sont des index reconstruisibles. À terme : Git → packages → validation/hash → index → TypeScript Research Catalog. Le DB n'est jamais la recherche elle-même.
18. Identité, attribution et signatures. Pseudonyme stable possible; identité cryptographique séparée du nom affiché. Une extension ou expérience dérivée conserve la provenance de ses créateurs. Importer le travail de quelqu'un ne transforme jamais ce travail en contribution du nouvel auteur. Plus tard, signatures de packages/messages et éventuellement identité organisationnelle vérifiée.
19. Sécurité des extensions. Permissions explicites et sandbox : experiment.read, workspace.read/write, model.inference, network, subprocess, etc. Un Tool avec shell/réseau est beaucoup plus risqué qu'un Thinker textuel. Pas de secrets, fichiers personnels, environnement complet ou privilèges administrateur. Le modèle qui écrit une extension n'a jamais le droit de l'activer lui-même.
20. Open Extension API/SDK, Stable Core protégé. Workers/Thinkers/Tools communautaires communiquent avec une API stable. On peut garder le projet open source tout en imposant PR, CI, tests et review pour Core. L'objectif concret : une personne extérieure crée un Worker, te l'envoie, tu l'importes et l'utilises sans modifier une seule ligne du Stable Core.
La séquence que je suivrais maintenant est donc :
Tetris/Code Lab fonctionnel → visualisation live des agents → baseline totalement vert → migration TypeScript → Research Layer V1 + .lmresearch → Extension Lab/Bank + .lmextension → Single/Multi/Comparison → Catalog/échange entre deux installations → seulement ensuite communauté à grande échelle.
