LIFE_MEAN LABS

repository without exposing private research data, credentials, machine-specific

If the private repository or its Git history may ever have contained secrets,
private RAW, tokens, credentials, personal paths, local research data, or sensitive
collaboration artifacts, create a CLEAN public repository/export instead of
publishing the old Git history.

DO NOT PUSH OR PUBLISH AUTOMATICALLY.
Produce a release-ready sanitized tree and an audit report.

PROMPT 2 — FUTURE CLIENT/SERVER COLLABORATION ARCHITECTURE
======================================================================

LIFE_MEAN LABS
DISTRIBUTED COLLABORATION — CLIENT / RENDEZVOUS SERVER / REMOTE EXECUTOR

MISSION

Design the future Life_mean collaboration architecture.

DESIGN ONLY unless a later task explicitly authorizes implementation.

Goal:

Two or more independent Life_mean Labs may collaborate in one experiment while:

- retaining local-first operation
- keeping private Lab memory private
- sharing only explicitly approved experiment data
- preserving an equal local copy of the shared experiment for participants
- allowing each node to contribute models, Workers, Tools, templates or compute
- protecting traffic from passive interception
- preserving provenance and reproducibility
- requiring explicit human acceptance before participation

----------------------------------------------------------------------
1. ROLES
----------------------------------------------------------------------

LIFE_MEAN CLIENT / NODE

Owns:
- local models
- local Workers/Tools
- local private RAW
- local Notebook
- local DB
- local permissions
- accept/decline authority

COLLAB RENDEZVOUS SERVER

Owns only what is needed for:
- presence
- node discovery
- invitation delivery
- session negotiation
- compatibility metadata
- minimal connection metadata

It should NOT become the canonical owner of private research.

COORDINATOR NODE

For one collaborative run, one participant becomes Coordinator.

Coordinator owns:
- canonical experiment/run state
- turn/stage order
- lifecycle
- budgets
- canonical EventBus decisions
- validation of remote results
- canonical shared-run manifest

REMOTE NODE

Executes only approved bounded requests and returns structured results.

----------------------------------------------------------------------
2. USER EXPERIENCE
----------------------------------------------------------------------

When a collaborator proposes a session:

LIFE_MEAN COLLAB PROPOSAL

From:
<identity / pseudonym>

Experiment:
<title>

Requested capabilities:
- model X
- Worker Y
- Tool Z
- template A

Estimated:
- max turns
- approximate runtime
- allowed tool calls
- data categories requested

Shared during session:
explicit list

Stored locally after session:
explicit list

Never shared automatically:
explicit list

Actions:

[ INSPECT ]
[ ACCEPT ]
[ DECLINE ]

No execution before ACCEPT.

----------------------------------------------------------------------
3. CONSENT SNAPSHOT
----------------------------------------------------------------------

At acceptance/create-run time freeze:

participants
node identities
requested capabilities
approved capabilities
data-sharing policy
retention policy
protocol/config snapshot
budgets
permissions
transport mode
coordinator identity

The active run may not silently broaden permissions.

Any material permission/data-sharing change requires new approval or a branch/new run.

----------------------------------------------------------------------
4. DATA ZONES
----------------------------------------------------------------------

Keep separate:

PRIVATE_LOCAL
- private RAW
- Notebook
- Ledger
- unrelated files
- secrets
- unrelated experiments

COLLAB_SHARED
- approved conversation/context
- approved model outputs
- approved tool results
- validator results
- protocol/config snapshot
- shared artifacts
- provenance
- shared run events

PUBLIC
- only explicitly sanitized/published exports

Never infer:
COLLAB_SHARED == PUBLIC.

----------------------------------------------------------------------
5. CONTEXT FIREWALL
----------------------------------------------------------------------

Before any outbound remote execution:

FULL LOCAL STATE
        ↓
Context Firewall
        ↓
minimum approved bounded state
        ↓
Remote ExecutionRequest

The firewall should enforce:
- allowlisted fields
- denylisted private classes
- path redaction
- secret filtering
- experiment scope
- participant consent
- capability-specific minimum context

Remote nodes receive only what they need.

Encryption does not replace minimization.

----------------------------------------------------------------------
6. TRANSPORT SECURITY
----------------------------------------------------------------------

For V1, strongly consider:

Tailscale / WireGuard private networking

Benefits:
- encrypted transport
- no direct public port exposure required
- simpler peer connectivity
- practical friend/lab collaboration

Do not hardwire Life_mean permanently to one transport.

Abstract transport behind a CollaborationTransport interface.

Tailscale protects transport.
Life_mean still needs application authorization.

----------------------------------------------------------------------
7. APPLICATION SECURITY
----------------------------------------------------------------------

Every session/request should conceptually include:

session_id
request_id
sender_node_id
receiver_node_id
sequence_number
timestamp / expiry
capability_id
payload hash
policy snapshot reference

Reject:
- unknown node
- expired session
- duplicated/replayed request
- unauthorized capability
- data outside approved scope
- budget overflow

Future option:
message signatures / node signatures.

Do NOT invent custom cryptography.

----------------------------------------------------------------------
8. REMOTE EXECUTION CONTRACT
----------------------------------------------------------------------

Preferred shape:

ExecutionRequest
- session_id
- run_id
- step_id
- objective
- bounded state/context
- requested capability
- expected result/schema
- budget
- permissions

ExecutionResult
- request_id
- status
- actual node
- actual model/tool/worker
- structured result
- artifacts allowed for sharing
- errors
- timing
- provenance
- result hash

Remote result is not automatically accepted as truth.
Coordinator validates it.

----------------------------------------------------------------------
9. SHARED RUN REPLICATION
----------------------------------------------------------------------

For equitable collaboration:

the approved COLLAB_SHARED run record should be persisted locally by all
participants who opted into retention.

Example:

PC A:
shared_run_hash = ABC

PC B:
shared_run_hash = ABC

Private Notebook interpretation may differ.

Core principle:

SHARED EVIDENCE.
INDEPENDENT PRIVATE INTERPRETATION.

----------------------------------------------------------------------
10. EVENT INTEGRITY
----------------------------------------------------------------------

Future shared event stream may be append-only/hash-linked:

event_id
previous_event_hash
payload_hash
sender_node
timestamp

At run finalization create a shared manifest containing:

run_id
participants
protocol/config hash
final event hash
artifact hashes
capability versions
actual models/nodes

Future signing may be added later.

Do not build blockchain or distributed consensus unnecessarily.

----------------------------------------------------------------------
11. DISCONNECTION
----------------------------------------------------------------------

Define explicit behavior for:

remote node disconnect
coordinator disconnect
timeout
participant leaves
capability disappears
network partition
rejoin

Never silently fabricate completion.

Possible outcomes:

WAITING_FOR_REMOTE
REMOTE_UNAVAILABLE
PARTICIPANT_LEFT
INCONCLUSIVE
FAILED
STOPPED

----------------------------------------------------------------------
12. LOCAL-FIRST REQUIREMENT
----------------------------------------------------------------------

If rendezvous server disappears:

local Life_mean must still work.

Existing local experiments must remain usable.

The collaboration server is optional infrastructure, not the core Lab.

----------------------------------------------------------------------
13. FUTURE COLLAB MODES
----------------------------------------------------------------------

LOCAL EXPERIMENT
one Lab

DISTRIBUTED EXPERIMENT
multiple machines controlled by one Lab

COLLABORATIVE EXPERIMENT
multiple independent Labs
+ explicit consent
+ shared evidence
+ independent private memory

----------------------------------------------------------------------
14. OUTPUT
----------------------------------------------------------------------

Produce a design document only:

DISTRIBUTED_COLLAB_ARCHITECTURE.md

Include:

- trust boundaries
- data flow
- threat model
- consent flow
- client/server responsibilities
- Context Firewall
- remote execution contract
- shared-run storage
- disconnect behavior
- Tailscale V1 integration point
- future transport abstraction
- what MUST remain local

NO IMPLEMENTATION unless explicitly authorized.
