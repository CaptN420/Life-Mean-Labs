======================================================================
0. NORTH STAR
======================================================================

Life_mean should become a local-first, controlled experimental environment
for designing, executing, observing, comparing, preserving, and eventually
sharing AI experiments.

The system is NOT limited to Coding or Philosophical Debate.

Target loop:

QUESTION / PROMPT
    ↓
DESIGN EXPERIMENT
    ↓
HUMAN REVIEW
    ↓
START
    ↓
IMMUTABLE EXECUTION SNAPSHOT
    ↓
EXECUTE STAGES / LOOPS
    ↓
DETERMINISTIC VALIDATION FIRST
    ↓
RESULT
    ↓
ANALYSIS
    ↓
RAW / METRICS / DB / JOURNAL / FAILURE BANK
    ↓
COMPARE
    ↓
FOLLOW-UP EXPERIMENT / REPAIR CANDIDATE

Main principle:

AI proposes.
Life_mean controls execution.
Deterministic evidence has priority.
Loops are bounded.
Humans retain authority.
RAW records what actually happened.
Everything else is interpretation.

======================================================================
1. NON-NEGOTIABLE CORE PRINCIPLES
======================================================================

1. Preserve the Stable Core.
2. Experimental layers USE the Stable Core; they do not duplicate it.
3. Deterministic-first; LLM when needed.
4. MODEL != ROLE != PERSONA != SKILL != TOOL.
5. MCP != Orchestrator.
6. Configured/available model != actual model used.
7. LLMs may request capabilities; they cannot authorize themselves.
8. Human approval is required for dynamic incorporation or risky runtime changes.
9. Scientific execution must remain traceable to RAW.
10. Observation != Hypothesis != Recommendation.
11. Research packages carry evidence.
12. Extension packages carry executable capabilities.
13. Downloaded extension != incorporated extension.
14. Never encode the research hypothesis as architecture.
15. Never report fake success, fake executor support, fake routing, or fake UI activity.
16. Historical runs remain immutable.
17. Do not expose secrets in logs, packages, or RAW exports.

3. DEVELOPMENT ORDER / DEPENDENCY ROADMAP
======================================================================

M0 — STABILIZE + OBSERVE
------------------------
Before adding a large autonomous-looking system, make execution trustworthy.

Goals:
- finish/freeze the current baseline
- keep dashboard/API/Core/RAW chain working
- wheel/installability and resources correct
- remove machine-specific paths
- lifecycle race fixes
- Code Lab dependency injection
- Settings truly connected
- Autopilot truly accessible
- clean tests
- real semantic execution logs
- live agent timeline based on EventBus

Observability must answer:
WHAT is running?
WHY?
WHO?
WHICH model/tool?
WHAT happened?
DID it work?
WHY retry/escalate/stop?
WHAT was stored?

HTTP 200 is infrastructure feedback.
Life_mean needs experiment feedback.

M1 — COMPARE V1 + EXECUTOR/ORCHESTRATOR REGISTRY
--------------------------------------------------
Build Compare early because later research, routing, model specialization,
and post-training all depend on measurement.

Compare should:
- compare multiple experiments/runs
- identify common and changed variables
- classify comparability
- detect failure patterns
- separate OBSERVATION / HYPOTHESIS / REPAIR_CANDIDATE
- work deterministically when LLM analysis is unavailable
- never claim causality from uncontrolled comparisons

Also:
- audit useful orchestrator logic from the external/legacy orchestrator folder
- integrate only through adapters/registry, not by duplicating Stable Core
- expose orchestrator/executor selection in Settings where appropriate

M2 — FRONTEND/API FOUNDATION
----------------------------
Migrate the large dashboard progressively toward a modular TypeScript UI
after the backend/API contract is stable enough.

Suggested pages:
- Debate
- Autopilot
- Code Lab
- Settings
- Sandbox
- Compare
- Research
- Extensions

Python remains the engine.
TypeScript becomes the interchangeable UI.

M5 — SMALL-MODEL CONTROL PLANE
------------------------------
Use small local models as specialized infrastructure rather than asking one
large model to do everything.

Candidate logical roles:
- micro Narrator / Trace Summarizer (~0.6–0.8B)
- Intent Router (~0.8B)
- Experiment Designer (~0.8B)
- micro specialists: math/bio/coder/etc.
- Lab Manager (~1.7B or larger), called only on escalation

No model name should be hardcoded.
These are roles assigned through Settings/model pools.

----------------------------------------------

- Compare parent vs candidate
- promote/reject explicitly
- allow rollback to base/previous generation

The Lab Manager may learn continuously through DB/memory, while weight updates
remain checkpointed and experimentally evaluated.

======================================================================
4. EXPERIMENTAL SANDBOX — DESIGN MODE
======================================================================

The Sandbox has an AI COPILOT.

The Copilot helps the researcher DESIGN an experiment from natural language.

Example:

"Explore an interesting computer science problem.
Let several agents research it, debate possible solutions,
test what can be tested, and stop when we have either a supported
answer or an inconclusive result."

The Copilot may propose:

INPUT
 ↓
Subject Generator
 ↓
Research
 ↓
Team Generator
 ↓
Solve / Debate Loop
 ↓
Validation
 ↓
Result Analyzer
 ↓
Curator / Finalize

This is ONLY a proposal.

Before Start, the experiment is a mutable workspace:

DRAFT

The researcher may:
- edit the initial prompt
- chat with the Copilot
- add/remove/reorder stages
- add/remove agents
- generate roles/personas
- edit system prompts
- select fixed models or pools
- change routing
- change validators
- change Skills/Tools
- change permissions
- change loops/budgets
- change escalation rules
- remove useless LLM stages
- add deterministic stages

The Copilot may suggest structural changes but does not silently apply
important changes.

Key rule:

DO NOT FREEZE CREATIVITY.
FREEZE REPRODUCIBILITY.

5. START IS THE AUTHORITY BOUNDARY
======================================================================

Nothing should execute simply because:
- a team was generated
- roles were generated
- personas were generated
- models were selected
- a pipeline was proposed

When the researcher presses:

[ START EXPERIMENT ]

then:

DRAFT
 ↓
VALIDATE DESIGN
 ↓
CREATE EXECUTION SNAPSHOT
 ↓
FREEZE SNAPSHOT
 ↓
RUNNING

Snapshot:
- complete pipeline
- stage order/config
- roles
- personas
- Skills
- system prompts
- prompt hashes
- models/pools
- routing rules
- variables
- validators
- Tools/MCP permissions
- loop rules
- budgets
- stop conditions
- versions/hashes

The editable draft may continue to exist for a future run.
The active run never silently changes.

Runtime Copilot suggestions must be explicit and recorded.

======================================================================

- Model Pool

science-micro-pool

Solver:
math pool

Escalation:
0.8B → 1.7B → 4B → multi-agent

Record separately:

CONFIGURED ROUTING
vs
ACTUAL ROUTING

For every actual model call record:
- configured model/pool
- actual model
- selection mode

AVAILABLE != USED.

======================================================================
11. SMALL-MODEL CONTROL PLANE
======================================================================

Use small models only for jobs where they provide value.

MICRO NARRATOR / TRACE SUMMARIZER
- consumes real EventBus activity
- produces readable summaries
- does not define authoritative state

INTENT ROUTER
- classifies task/stage
- recommends pool/executor
- recommendation remains advisory

EXPERIMENT DESIGNER
- proposes workflow/roles/personas/skills/tools
- runs in Design Mode
- never auto-starts

MICRO SPECIALISTS
Examples:
- math
- biology
- coding
- domain-specific science

LAB MANAGER
- larger than micro models
- called only when needed
- stalled task
- conflicting evidence
- significant agent disagreement
- package interpretation
- repeated weakness
- missing capability
- researcher asks for deeper analysis

Manager does not replace deterministic validators.

All model choices remain configurable in Settings.

======================================================================

======================================================================
13. CONTROLLED LOOP ENGINE
======================================================================

Loops are explicit and always bounded.

Example:

LoopDefinition:
- stages: solve → validate → analyze_failure
- continue_when: result_unresolved
- stop_when:
  - validator_pass
  - max_iterations
  - budget_exceeded
  - no_progress
  - human_stop
- max_iterations: 5

Never implement:

while not solved:
    call_llm()

Every iteration records:
- iteration_id
- input state
- agents used
- actual models
- tools used
- result
- validation
- failure reason
- progress signal
- tokens/time/cost when available

Possible loop states:

ACTIVE
RESOLVED
STALLED
BUDGET_EXCEEDED
FAILED

If no supported answer is found, INCONCLUSIVE is a valid scientific outcome.

======================================================================
14. STAGNATION + ESCALATION
======================================================================

Detect:
- same answer repeated
- same validation failure
- no new evidence
- same patch repeatedly generated
- semantic repetition
- unchanged tool result
- budget pressure

Possible responses:
- use deterministic Tool
- change agent
- request Critic
- escalate model
- stop as INCONCLUSIVE

Escalation is policy-controlled.

Example:
0.8B
 ↓ fails twice
1.7B
 ↓ unresolved
specialist multi-agent
 ↓ unresolved
manager analysis
 ↓
INCONCLUSIVE

Models do not grant themselves unrestricted escalation.

======================================================================
15. DETERMINISTIC-FIRST CAPABILITY RESOLVER
======================================================================

Preferred resolution order:

1. deterministic active Tool
2. suitable Skill/instructions
3. existing Worker
4. existing Thinker
5. downloaded deterministic capability requiring human approval
6. small specialist model
7. multi-agent reasoning
8. larger model

Example:
Need = validate JSON

If JSONSchemaValidator exists:
use it.

Do not ask five agents whether the JSON "looks correct".

Deterministic validation and semantic judgment remain separate.

======================================================================
16. SKILLS
======================================================================

A Skill is not a model and not an executable Tool.

Skill contains:
- instructions
- workflow knowledge
- schemas
- best practices
- domain-specific context
- optional recommended Tools
- required permissions metadata

Skills should be:
- versioned
- hashable
- portable
- reusable across models
- included in experiment provenance

Example:
pytest-debugging
- instructions
- recommended tools: tests.run, workspace.read_file, workspace.write_patch
- permissions: workspace.read, workspace.write

======================================================================
17. MCP + TOOL ACCESS
======================================================================

MCP is a standardized interface for capabilities/resources.

MCP does NOT replace:
- EventBus
- SmartRouter
- DebateEngine
- Life_mean orchestration
- agent-to-agent protocol

Concept:

Agent ↔ Agent
Life_mean protocol

Agent ↔ Tool / Resource
MCP / capability adapter

A model running in LM Studio does NOT automatically have Tools.

Path A — native tool/function calling:
Life_mean exposes definitions
→ model requests
→ Life_mean validates
→ Tool/MCP executes
→ result returned

Path B — structured tool request:
model emits structured request
→ Life_mean parses
→ validates schema/permissions/policy
→ executes
→ records to RAW
→ returns result

The model never receives arbitrary host access.

Permissions may include:
- workspace.read
- workspace.write
- experiment.read
- memory.read
- subprocess
- network
- git.local
- package.read

36. FIRST SANDBOX ACCEPTANCE SCENARIO
======================================================================

User enters:

"Generate an interesting computer science research subject and investigate
it until the team reaches either a supported answer or an inconclusive result."

1. Copilot proposes a workflow.
2. Nothing executes.
3. User edits stages/models/roles/personas/prompts/loops.
4. User presses START.
5. Life_mean validates and snapshots the exact design.
6. Subject Generator creates a subject.
7. Team Generator proposes/creates permitted roles for the active design.
8. Research/Solver stages execute.
9. Deterministic Validator evaluates progress.
10. If unresolved, bounded loop continues.
11. If stagnated, policy controls escalation or INCONCLUSIVE.
12. If resolved, Result Analyzer runs.
13. Curator/Manager organizes useful information.
14. Finalization writes RAW, metrics, results, observations, hypotheses,
    failures, notes, follow-ups, and DB relationships.
15. Compare can later evaluate the run against other conditions.
